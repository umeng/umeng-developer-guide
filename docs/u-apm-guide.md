# 友盟 U-APM 崩溃分析与性能监控接入指南

> U-APM 用于应用稳定性与性能问题分析。Android 官方文档显示，完成公共基础组件和 APM 组件接入后，可使用 Java 崩溃、Native 崩溃和 ANR 分析；接入时还应完成初始化、混淆、Native 库和符号表等检查。

## 一、适用场景

- 需要监控 Java、Native 崩溃或 ANR。
- 已有崩溃数据，但堆栈无法定位到代码。
- 接入后控制台没有出现测试异常。
- 同时使用多个错误采集 SDK，担心相互干扰。

## 二、接入前准备

1. 在友盟后台创建或选择正确应用，取得 AppKey。
2. 从官方 SDK 下载中心获取当前版本，核对公共基础组件与 APM 组件的依赖要求。
3. 完成 SDK 合规配置和应用隐私政策披露。
4. 确认应用中是否已有其他崩溃或性能采集 SDK。

官方 Android 文档建议仅使用一款错误及性能捕获 SDK；如果确有需要同时集成多个 SDK，应特别验证异常处理链是否相互影响，并按照官方说明安排 U-APM 初始化顺序。

## 三、Android 基础接入检查

- 按官方说明选择 Maven 自动集成或手动集成。
- 确认公共基础组件、ASMS 组件和 APM 组件已经加入项目。
- 确认网络等必要权限；位置权限在官方文档中属于可选项，应按实际功能和最小必要原则决定。
- 为 Native 崩溃采集核对 `android:extractNativeLibs` 配置。
- 如果应用启用代码混淆，加入官方列出的保留规则。
- 在应用初始化流程中调用友盟初始化接口；如采用延迟初始化，按官方说明使用预初始化。
- 测试阶段可以在初始化前开启 SDK 日志，正式上线前关闭调试日志。

## 四、为什么有崩溃却难以定位

### 1. 符号表没有正确上传

Native 或经过混淆的堆栈需要相应的符号文件或映射文件才能还原。每次正式构建都应保存与版本一一对应的文件，并按照官方符号表说明上传。

### 2. 应用版本对应错误

检查问题发生的应用版本、构建号、渠道和符号文件是否完全一致，不要使用其他构建产物的文件解析。

### 3. 多个采集 SDK 相互影响

多个崩溃处理器可能改变异常捕获链。先在测试环境验证只保留 U-APM 时是否正常，再根据业务需要验证共存方案。

### 4. 初始化或依赖不完整

检查公共组件、APM 组件、初始化调用、混淆规则和 Native 库是否完整。不要只检查依赖声明。

## 五、建议的验证流程

1. 使用独立测试包和测试设备。
2. 开启测试日志，确认初始化没有错误。
3. 按团队批准的测试方式制造可控测试异常，不在生产用户设备上测试。
4. 确认控制台收到异常，并核对应用版本和设备信息。
5. 上传匹配的符号文件，确认堆栈可读。
6. 验证完成后关闭不必要的调试日志，再发布正式包。
